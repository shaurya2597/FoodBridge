# FoodBridge frontend

The website that people see: browse restaurants, order food, donate surplus food, and (for staff) manage everything.
It talks to the FoodBridge backend (`../backend`) over its REST API and Socket.IO. **Milestone M0** (this version) only
proves the plumbing works: it shows an "API connected" page. More screens arrive milestone by milestone.

## Commands (run these inside the `frontend` folder, in Windows PowerShell)

| Command | What it does |
|---|---|
| `npm.cmd run dev` | Starts the website at http://localhost:5173 (needs the backend running too) |
| `npm.cmd run typecheck` | Checks every TypeScript file for mistakes without running anything |
| `npm.cmd run test` | Runs the automatic tests (Vitest) |
| `npm.cmd run check:security` | Fails if a security rule below is broken |
| `npm.cmd run build` | Makes the optimised production version in `dist/` (also type-checks) |
| `npm.cmd run verify` | Runs typecheck, security check, tests and build, in that order |

## Settings

Copy `.env.example` to `.env` (in this folder). The only setting is `VITE_API_URL` (default `http://localhost:5000/api`).
Everything starting with `VITE_` is copied into the public website. **Never put a secret in it.**
The backend's own `.env` is a different file and is never touched by the frontend.

## How the code is organised

```
src/
  main.tsx, App.tsx, router.tsx   start-up, global providers, the address -> page map
  pages/                          one file per screen
  components/ui/                  shadcn/ui building blocks (buttons, cards...), generated by the shadcn tool
  services/                       everything that talks to the backend
    apiClient.ts                  the ONE function that calls the backend (adds the token, converts errors)
    apiError.ts                   one error type for every failure + friendly messages
    tokenStorage.ts               the ONE place the login token is stored
    health.ts                     asks the backend "are you alive?"
  types/api.ts                    the shape of data the backend sends
  utils/                          small helpers (settings checking)
  test/setup.ts                   test helper set-up
```

## Security notes

**Where the login token lives and why.** After login the backend gives the browser a token (a signed ticket). We keep it in
the browser's `localStorage` so you stay logged in after refreshing the page. The trade-off: if an attacker ever managed to
run their own script inside our page (called XSS), that script could read the token. The safer alternative, an `httpOnly`
cookie, cannot be read by scripts, but it needs backend changes (cookies, CSRF protection), so for this project we accept
`localStorage` and reduce the risk instead:

1. **One place only.** Only `services/tokenStorage.ts` may touch storage, and only `services/apiClient.ts` attaches it to requests.
2. **Never shown or logged.** The token is never printed, never put in a URL, never copied into error objects.
3. **Cleared promptly.** It is removed on logout, when the server answers 401 (session ended), when it expires, and when it looks malformed.
4. **No unsafe HTML.** The app never uses `dangerouslySetInnerHTML`, `innerHTML` or `eval`. React escapes text automatically.
5. **No secrets in the frontend.** Payment verification stays on the server, and no Razorpay secret key exists in this project.
6. **Checked automatically.** `npm.cmd run check:security` fails if any of these rules are broken, and it runs as part of `verify`.

Other things worth knowing: a production deployment should also send a Content-Security-Policy header (added in the final
milestone); and the backend can end all of a user's sessions at once ("log out everywhere", password change), which this app respects.
